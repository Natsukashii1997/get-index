# KB-04｜GET 增量维护闭环 Spec

**Status:** ready-for-agent

**Parent project:** Obsidian 人生知识库 `KB-04`

## Problem Statement

当前 GET 来源索引是 2026-09-15 的 168 篇静态快照。GET 插件以后继续同步新笔记或更新既有笔记时，索引不会自动知道发生了什么；若每次重新扫描、重新判断并重新总结全库，既浪费 Token，也增加错误重分类和改坏只读来源的风险。

常浩需要一个可审计、失败关闭的增量闭环：先只读识别变化，只让少量新增或真正影响索引的数据进入复核，验证全部通过后才更新来源层之外的索引；任何异常都不能修改 `GET NOTES/**`，也不能把未扫描、未分类或失败状态伪装成“无新增”。

## Solution

建立一个本地、人工可控的两阶段增量流程：

1. **检测阶段只读。** 对当前 GET Markdown 建立轻量清单，与上次已接受快照比较，区分新增、路径／关键元数据变化、仅内容变化、缺失和无变化，并生成清晰报告。该阶段不得写 Vault。
2. **复核阶段保守。** 新增或影响索引的变化只生成待复核记录；能从 frontmatter 确认的事实自动带入，无法可靠判断的领域和敏感性从严处理，不调用 AI 批量重做已有 168 篇。
3. **应用阶段受控。** 只有待复核记录完整、当前来源仍与检测基线一致、全量结构校验通过时，才一次性更新来源层之外的规范记录和索引页。任一检查失败则全部不应用，快照不推进。
4. **人工运行优先。** 首版提供非技术使用说明和单一入口，先用无新增现场与外部测试夹具验证；定时或事件触发不在本 Spec 内，待稳定性和维护成本有证据后另行决定。

## User Stories

1. 作为知识库所有者，我希望一次运行就能看到 GET 是否出现新增、变化或缺失，这样不需要手工翻日期目录，也不会因为“没有提示”误以为索引仍是最新的。
2. 作为知识库维护者，我希望在没有变化时得到明确的零变更报告，且任何 Vault 内容都不被重写，这样可以安全、低成本地重复检查。
3. 作为知识库维护者，我希望新增来源只生成一条保守的待复核候选，并复用已有 frontmatter 事实，这样只把少量真正新增内容交给人工或按需 AI 判断。
4. 作为知识库维护者，我希望既有来源发生内容变化时被记录，但不会自动推翻原领域、敏感性和主题，这样同步更新不会造成静默重分类。
5. 作为知识库所有者，我希望缺失来源、重复 UID、frontmatter 解析失败、检测后又发生变化或待复核字段不完整时系统停止应用，这样失败不会被包装成成功，也不会留下半更新索引。
6. 作为非技术使用者，我希望运行结束时看到“发现了什么、是否改动、下一步需要我做什么”，这样不必阅读代码或日志就能判断成功与否。

## Implementation Decisions

- 以现有规范记录作为已接受的分类事实，不重新推断 168 篇历史来源。
- 快照只保存检测所需的最小元数据：来源相对路径、UID、索引相关 frontmatter 值和内容哈希；不复制总结、转写或正文。
- 变化分为五类：`added`、`index_metadata_changed`、`content_only_changed`、`missing`、`unchanged`。路径或 UID 变化不自动视为删除加新增，先作为高风险变化停止应用。
- `content_only_changed` 只更新变化报告；除非真实问题或人工复核证明分类需要调整，否则沿用原规范记录。
- 新增来源的事实字段来自 frontmatter。无法可靠确认的治理字段进入待复核；敏感性默认 `受限`，不得为了消灭待复核而读取完整转写。
- 检测与应用使用显式的两个命令／阶段。检测产物带基线指纹；应用前重新读取当前来源，指纹不一致即拒绝应用。
- 应用前先在临时位置生成全部目标页并运行完整校验；全部通过后再替换来源层之外的索引文件。任何失败都不推进已接受快照。
- 所有用户可见统计从当前规范记录动态生成，移除固定日期和固定“168”文案。
- 默认不调用外部服务，不连接远程，不发送 Vault 内容，也不创建定时任务。
- 项目工作卡是业务状态事实源；本地 Spec、Ticket、测试和版本记录是 KB-04 技术证据，完成后必须回写工作卡。

## Testing Decisions

- 主要测试 seam 设在命令行行为边界：给定临时来源树、已接受规范记录和快照，验证退出码、结构化报告、候选变更和最终索引结果，而不是锁定内部函数实现。
- 所有会制造新增、删除、重复、损坏 frontmatter 或并发变化的测试都使用临时夹具，不在真实 `GET NOTES/**` 创建测试文件。
- 至少覆盖：无变化零写入；单个新增；仅正文变化；索引相关元数据变化；来源缺失；重复 UID；损坏 frontmatter；待复核字段不完整；检测后来源变化；应用前校验失败。
- 验证幂等性：同一已接受输入重复运行，报告稳定且不会产生内容差异。
- 真实 Vault 只执行只读无变化检测，并在任何应用前后核对 GET Markdown 的逐文件哈希；首个真实新增来源需等 GET 正常同步后再做验收，不制造假来源。
- 现有全量校验器继续作为回归门；新增测试需证明动态渲染不降低 168 篇覆盖、唯一性、枚举、主题和回链约束。

## Out of Scope

- 修改、移动、重命名、删除或回写 `GET NOTES/**`。
- 读取音频、批量读取完整转写，或为每篇 GET 再生成一份总结。
- 自动决定所有新增来源的领域、敏感性和主题；低置信度必须进入复核。
- 批量重分类既有 168 篇规范记录。
- 创建定时任务、文件监听器或通知自动化。
- Codex 历史知识导入、机械邪龙兽、团队飞书及微信／小红书／抖音接入。
- 建立远程 Git 仓库、上传数据或发布代码。

## Further Notes

- 现有来源快照为 168 篇：生活 7、工作／个人 21、工作／团队 140；待复核 1。它们是本功能的迁移基线，不是重新分类输入。
- 唯一缺少 GET 总结的既有来源继续保持受限待复核；本功能不得为消灭该状态而通读完整转写。
- 本 Spec 固定“人工先行、调度后决策”的首版边界。是否自动运行取决于后续真实新增验收、失败恢复和单次维护成本，不在当前 Ticket 中偷偷加入。
- Ticket 拆分和 blocking edges 经常浩确认后再发布；确认前不进入实现。
